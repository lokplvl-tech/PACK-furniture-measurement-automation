## [FMA.M.004] RAG-подсказчик дизайнера-конструктора: обещание, сценарии, режим отказа

### Definition

Итог IntegrationGate (06.08.2026) по предложению собственной базы поиска и подстановки знаний (RAG), позволяющей роли «Дизайнер-конструктор» ([FMA.R.001](../02-domain-entities/01B-roles.md#fma-r-001)) собирать рабочие Базис-скрипты по каталогам поставщиков и проверенным приёмам API, вместо ручного чтения PDF и подбора параметров вслепую при каждом новом заказе. Решения по всем трём шагам (обещание/сценарии/роль) - от пилота, не додуманы агентом.

### Обещание (Service Clause)

| Поле | Значение |
|---|---|
| **Триггер** | Запрос роли «Дизайнер-конструктор» (сейчас - пилот; в перспективе - голосовая команда будущего агента в этой роли) на построение фасада/модуля под конкретный размер и узор |
| **Входы** | Технические характеристики из каталогов поставщиков (например `RS GROUP`), реальные размеры заказа, выбранный узор/тип панели |
| **Выход** | Готовый рабочий файл `BAZIS-Script` под конкретный размер/узор **и** попытка его запуска в Базис-Мебельщике - не только текст скрипта, но и подстановка/исполнение |
| **Инвариант** | Используются только проверенные приёмы API - реальный боевой пример (`Example/Моя первая тумбочка 2.js`) и зафиксированные предостережения ([FMA.GRD.001](../05-failure-modes/FMA.GRD.001.md)-[003](../05-failure-modes/FMA.GRD.003.md)). При отсутствии проверенного приёма для конкретной геометрии - система честно останавливается, не строит наугад |
| **Режим отказа** | При неуверенности или недостатке проверенных данных - результат выдаётся с явным открытым вопросом к роли «Дизайнер-конструктор», не тихой достройкой решения |

**Обоснование инварианта - прямое, не абстрактное.** Три предостережения ([FMA.GRD.001-003](../05-failure-modes/)) - реальные поломки той самой сессии, где этот RAG-подсказчик придуман: скрипт падал с непонятной ошибкой, строил перекошенную деталь без единого сообщения об ошибке, неверно понимал параметр толщины. Обещание «не строить наугад» - не формальность, а прямой урок этого же дня.

### Сценарии использования (минимум 3, по решению пилота)

1. **Пилот запрашивает сам (текущий режим).** Пилот формулирует размер/узор заказа → получает файл скрипта → сам проверяет результат в Базис-Мебельщике, сообщает об ошибках или успехе.
2. **Дизайнер присылает исходные данные.** Дизайнер (например, Евгений) присылает фото/чертёж с размерами и узором клиента → RAG-подсказчик собирает скрипт-кандидат → дизайнер проверяет и правит дополнительными инструкциями. Инструмент не считает свой первый результат финальным.
3. **Будущий голосовой агент в роли «Дизайнер-конструктор».** Агент получает голосовую команду → использует ту же базу знаний → сам строит и пробует запустить скрипт в Базис-Мебельщике → докладывает результат. Роль человека смещается на финальную проверку, не на ручной ввод параметров.
